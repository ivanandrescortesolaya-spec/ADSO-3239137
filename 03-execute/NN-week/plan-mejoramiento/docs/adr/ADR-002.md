# ADR-002 — Gestión de transacciones y concurrencia

## 1. Información general

| Campo | Valor |
|---|---|
| Identificador | ADR-002 |
| Proyecto | Music School |
| Fecha | 09/11/2026 |
| Versión | 1.0 |
| Estado | Aceptada |
| Categoría | Integridad de datos y concurrencia |

## 2. Contexto

Music School permitirá registrar préstamos y devoluciones de instrumentos musicales.

Estas operaciones modifican las unidades disponibles del inventario y deben mantener la integridad de la información almacenada en MySQL.

El sistema contempla la posibilidad de que varios operadores realicen solicitudes simultáneas sobre un mismo instrumento.

Por ejemplo, cuando solamente existe una unidad disponible, dos operadores podrían intentar registrar un préstamo al mismo tiempo.

Si ambas operaciones se ejecutan sin mecanismos de control, podrían ocasionar inconsistencias en el inventario y permitir que se preste una unidad que ya no está disponible.

## 3. Problema

Se necesita establecer un mecanismo que permita controlar las operaciones simultáneas sobre los préstamos y el inventario.

La solución debe garantizar que:

- No se presten más unidades de las disponibles.
- Las unidades disponibles nunca sean negativas.
- Las operaciones de préstamo y devolución mantengan la integridad de los datos.
- Las solicitudes concurrentes que no puedan completarse reciban una respuesta HTTP 409 Conflict.
- Los cambios parciales no permanezcan almacenados cuando una operación falle.

## 4. Decisión

Se adopta el uso de transacciones de base de datos y bloqueos de registros mediante Laravel, utilizando el mecanismo `lockForUpdate()` dentro de una transacción.

### 4.1. Registro de préstamos

El proceso de préstamo deberá realizar las siguientes operaciones:

1. Iniciar una transacción.
2. Bloquear el registro del estudiante y del instrumento involucrados, siguiendo un orden de bloqueo consistente.
3. Consultar nuevamente la información después de obtener los bloqueos.
4. Verificar que el instrumento esté activo y tenga unidades disponibles.
5. Verificar que el estudiante no tenga un préstamo pendiente de devolución ni préstamos vencidos que impidan una nueva operación.
6. Crear el registro del préstamo y conservar los datos históricos correspondientes.
7. Actualizar las unidades disponibles del instrumento.
8. Confirmar la transacción si todas las operaciones se ejecutan correctamente.
9. Revertir los cambios si ocurre un error.

Si otro operador ya ha prestado la última unidad disponible, la solicitud posterior deberá rechazarse con HTTP 409 Conflict.

### 4.2. Registro de devoluciones

El proceso de devolución deberá realizar las siguientes operaciones:

1. Iniciar una transacción.
2. Bloquear el registro del préstamo y del instrumento correspondiente.
3. Verificar que el préstamo exista y todavía no tenga una devolución registrada.
4. Crear el registro de devolución.
5. Incrementar las unidades disponibles del instrumento.
6. Verificar que las unidades disponibles no superen el total registrado.
7. Confirmar la transacción si todas las operaciones se ejecutan correctamente.
8. Revertir los cambios si ocurre un error.

La restricción de unicidad sobre `returns.loan_id` impedirá registrar más de una devolución para el mismo préstamo.

## 5. Alternativas consideradas

| Alternativa | Motivo para no seleccionarla |
|---|---|
| Actualizar el inventario sin transacciones | Una falla durante la operación podría dejar información parcialmente modificada. |
| Consultar la disponibilidad sin bloquear registros | Dos solicitudes simultáneas podrían leer la misma disponibilidad antes de que alguna actualice el inventario. |
| Controlar la concurrencia únicamente desde React | El frontend no puede garantizar la integridad de los datos frente a solicitudes simultáneas de diferentes clientes. |
| Utilizar bloqueos y transacciones en el backend | Se selecciona porque permite proteger las operaciones directamente en la base de datos y centralizar las reglas de negocio. |

## 6. Justificación

Las transacciones permiten agrupar las operaciones relacionadas con préstamos y devoluciones para que los cambios se confirmen de manera completa o se reviertan cuando ocurre un error.

El uso de `lockForUpdate()` permite bloquear temporalmente los registros involucrados mientras se ejecuta una operación dentro de una transacción.

La validación posterior a la obtención de los bloqueos evita utilizar información de disponibilidad que pudo haber cambiado por otra solicitud.

La respuesta HTTP 409 Conflict permite informar al cliente que la operación no puede completarse debido a un conflicto con el estado actual del recurso.

Esta decisión mantiene correspondencia con las reglas de negocio de `spec.md`, el modelo de datos de `data-model.md` y los procedimientos definidos en `api-contract.md`.

## 7. Consecuencias

### Consecuencias positivas

- Protección de la integridad del inventario.
- Prevención de préstamos por encima de las unidades disponibles.
- Evita que una operación incompleta deje cambios parciales.
- Control de solicitudes simultáneas sobre los mismos registros.
- Respuestas HTTP 409 para conflictos de disponibilidad.
- Conservación de la consistencia entre préstamos, devoluciones e inventario.

### Consecuencias y consideraciones

- Las transacciones deben mantenerse durante el menor tiempo posible.
- Los bloqueos pueden provocar esperas cuando existen operaciones simultáneas sobre los mismos registros.
- Se debe mantener un orden consistente al adquirir bloqueos para reducir el riesgo de interbloqueos.
- Es necesario gestionar los errores y revertir las transacciones cuando corresponda.
- La implementación debe probarse con solicitudes concurrentes para verificar su comportamiento.

## 9. Resultado

Se establece el uso de transacciones y bloqueos de registros en el backend para proteger las operaciones que modifican el inventario.

Las operaciones de préstamo y devolución deberán cumplir los procedimientos definidos en este registro para mantener la integridad de la información.

Este registro documenta una decisión arquitectónica y no constituye evidencia de que los mecanismos de concurrencia estén implementados o hayan superado pruebas.
