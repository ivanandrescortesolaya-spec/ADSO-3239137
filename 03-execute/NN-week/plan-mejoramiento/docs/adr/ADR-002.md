
# ADR-002 — Transaction and Concurrency Management

## 1. General Information

| Field | Value |
|---|---|
| Identifier | ADR-002 |
| Project | Music School |
| Date | 09/11/2026 |
| Version | 1.0 |
| Status | Accepted |
| Category | Data Integrity and Concurrency |

## 2. Context

Music School will allow the registration of musical instrument loans and returns.

These operations modify the available inventory units and must maintain the integrity of the information stored in MySQL.

The system considers the possibility of multiple operators making simultaneous requests involving the same instrument.

For example, when only one unit is available, two operators might attempt to register a loan at the same time.

If both operations are executed without control mechanisms, they could cause inventory inconsistencies and allow a unit that is no longer available to be lent.

## 3. Problem

A mechanism is needed to control simultaneous operations involving loans and inventory.

The solution must ensure that:

- No more units are lent than are available.
- Available units are never negative.
- Loan and return operations maintain data integrity.
- Concurrent requests that cannot be completed receive an HTTP 409 Conflict response.
- Partial changes are not retained when an operation fails.

## 4. Decision

The use of database transactions and row-level locking through Laravel is adopted, using the `lockForUpdate()` mechanism within a transaction.

### 4.1. Loan Registration

The loan process must perform the following operations:

1. Start a transaction.
2. Lock the student and instrument records involved, following a consistent locking order.
3. Retrieve the information again after acquiring the locks.
4. Verify that the instrument is active and has available units.
5. Verify that the student has no loan pending return or overdue loans that would prevent a new operation.
6. Create the loan record and preserve the corresponding historical data.
7. Update the instrument's available units.
8. Commit the transaction if all operations are executed successfully.
9. Roll back the changes if an error occurs.

If another operator has already lent the last available unit, the subsequent request must be rejected with HTTP 409 Conflict.

### 4.2. Return Registration

The return process must perform the following operations:

1. Start a transaction.
2. Lock the corresponding loan and instrument records.
3. Verify that the loan exists and does not already have a registered return.
4. Create the return record.
5. Increase the instrument's available units.
6. Verify that available units do not exceed the registered total.
7. Commit the transaction if all operations are executed successfully.
8. Roll back the changes if an error occurs.

The uniqueness constraint on `returns.loan_id` will prevent more than one return from being registered for the same loan.

## 5. Alternatives Considered

| Alternative | Reason for Not Selecting It |
|---|---|
| Update inventory without transactions | A failure during the operation could leave information partially modified. |
| Check availability without locking records | Two simultaneous requests could read the same availability before either updates the inventory. |
| Control concurrency only through React | The frontend cannot guarantee data integrity when simultaneous requests come from different clients. |
| Use locks and transactions in the backend | Selected because this approach protects operations directly at the database level and centralizes business rules. |

## 6. Justification

Transactions allow operations related to loans and returns to be grouped so that changes are either fully committed or rolled back when an error occurs.

Using `lockForUpdate()` temporarily locks the records involved while an operation is executed within a transaction.

Validation after acquiring the locks prevents the use of availability information that may have changed due to another request.

The HTTP 409 Conflict response informs the client that the operation cannot be completed because of a conflict with the resource's current state.

This decision is consistent with the business rules in `spec.md`, the data model in `data-model.md`, and the procedures defined in `api-contract.md`.

## 7. Consequences

### Positive Consequences

- Protection of inventory integrity.
- Prevention of loans exceeding available units.
- Prevention of partial changes caused by incomplete operations.
- Control of simultaneous requests involving the same records.
- HTTP 409 responses for availability conflicts.
- Preservation of consistency between loans, returns, and inventory.

### Consequences and Considerations

- Transactions must be kept as short as possible.
- Locks may cause waiting times when simultaneous operations involve the same records.
- A consistent lock acquisition order must be maintained to reduce the risk of deadlocks.
- Errors must be handled and transactions rolled back when appropriate.
- The implementation must be tested with concurrent requests to verify its behavior.

## 9. Outcome

The use of transactions and row-level locking in the backend is established to protect operations that modify inventory.

Loan and return operations must follow the procedures defined in this record to maintain data integrity.

This record documents an architectural decision and does not constitute evidence that the concurrency mechanisms have been implemented or successfully tested.
