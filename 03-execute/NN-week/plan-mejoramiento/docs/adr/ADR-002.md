# ADR-002 — Gestion de transacciones y concurrencia

## 1. Informacion general

| Campo | Valor |
|---|---|
| Identificador | ADR-002 |
| Proyecto | Music School |
| Fecha | 09/11/2026 |
| Version | 1.0 |
| Estado | Aceptada |
| Categoria | Integridad de datos y concurrencia |

## 2. Contexto

Music School permitira registrar prestamos y devoluciones de instrumentos musicales.

Estas operaciones modifican las unidades disponibles del inventario y deben mantener la integridad de la informacion almacenada en MySQL.

El sistema contempla la posibilidad de que varios operadores realicen solicitudes simultaneas sobre un mismo instrumento.

Por ejemplo, cuando solamente existe una unidad disponible, dos operadores podrian intentar registrar un prestamo al mismo tiempo.

Si ambas operaciones se ejecutan sin mecanismos de control, podrian ocasionar inconsistencias en el inventario y permitir que se preste una unidad que ya no esta disponible.

## 3. Problema

Se necesita establecer un mecanismo que permita controlar las operaciones simultaneas sobre los prestamos y el inventario.

La solucion debe garantizar que:

- No se presten mas unidades de las disponibles.
- Las unidades disponibles nunca sean negativas.
- Las operaciones de prestamo y devolucion mantengan la integridad de los datos.
- Las solicitudes concurrentes que no puedan completarse reciban una respuesta HTTP 409 Conflict.
- Los cambios parciales no permanezcan almacenados cuando una operacion falle.

## 4. Decision

Se adopta el uso de transacciones de base de datos y bloqueos de registros mediante Laravel, utilizando el mecanismo `lockForUpdate()` dentro de una transaccion.

### 4.1. Registro de prestamos

El proceso de prestamo debera realizar las siguientes operaciones:

1. Iniciar una transaccion.
2. Bloquear el registro del estudiante y del instrumento involucrados, siguiendo un orden de bloqueo consistente.
3. Consultar nuevamente la informacion despues de obtener los bloqueos.
4. Verificar que el instrumento este activo y tenga unidades disponibles.
5. Verificar que el estudiante no tenga un prestamo pendiente de devolucion ni prestamos vencidos que impidan una nueva operacion.
6. Crear el registro del prestamo y conservar los datos historicos correspondientes.
7. Actualizar las unidades disponibles del instrumento.
8. Confirmar la transaccion si todas las operaciones se ejecutan correctamente.
9. Revertir los cambios si ocurre un error.

Si otro operador ya ha prestado la ultima unidad disponible, la solicitud posterior debera rechazarse con HTTP 409 Conflict.

### 4.2. Registro de devoluciones

El proceso de devolucion debera realizar las siguientes operaciones:

1. Iniciar una transaccion.
2. Bloquear el registro del prestamo y del instrumento correspondiente.
3. Verificar que el prestamo exista y todavia no tenga una devolucion registrada.
4. Crear el registro de devolucion.
5. Incrementar las unidades disponibles del instrumento.
6. Verificar que las unidades disponibles no superen el total registrado.
7. Confirmar la transaccion si todas las operaciones se ejecutan correctamente.
8. Revertir los cambios si ocurre un error.

La restriccion de unicidad sobre `returns.loan_id` impedira registrar mas de una devolucion para el mismo prestamo.

## 5. Alternativas consideradas

| Alternativa | Motivo para no seleccionarla |
|---|---|
| Actualizar el inventario sin transacciones | Una falla durante la operacion podria dejar informacion parcialmente modificada. |
| Consultar la disponibilidad sin bloquear registros | Dos solicitudes simultaneas podrian leer la misma disponibilidad antes de que alguna actualice el inventario. |
| Controlar la concurrencia unicamente desde React | El frontend no puede garantizar la integridad de los datos frente a solicitudes simultaneas de diferentes clientes. |
| Utilizar bloqueos y transacciones en el backend | Se selecciona porque permite proteger las operaciones directamente en la base de datos y centralizar las reglas de negocio. |

## 6. Justificacion

Las transacciones permiten agrupar las operaciones relacionadas con prestamos y devoluciones para que los cambios se confirmen de manera completa o se reviertan cuando ocurre un error.

El uso de `lockForUpdate()` permite bloquear temporalmente los registros involucrados mientras se ejecuta una operacion dentro de una transaccion.

La validacion posterior a la obtencion de los bloqueos evita utilizar informacion de disponibilidad que pudo haber cambiado por otra solicitud.

La respuesta HTTP 409 Conflict permite informar al cliente que la operacion no puede completarse debido a un conflicto con el estado actual del recurso.

Esta decision mantiene correspondencia con las reglas de negocio de `spec.md`, el modelo de datos de `data-model.md` y los procedimientos definidos en `api-contract.md`.

## 7. Consecuencias

### Consecuencias positivas

- Proteccion de la integridad del inventario.
- Prevencion de prestamos por encima de las unidades disponibles.
- Evita que una operacion incompleta deje cambios parciales.
- Control de solicitudes simultaneas sobre los mismos registros.
- Respuestas HTTP 409 para conflictos de disponibilidad.
- Conservacion de la consistencia entre prestamos, devoluciones e inventario.

### Consecuencias y consideraciones

- Las transacciones deben mantenerse durante el menor tiempo posible.
- Los bloqueos pueden provocar esperas cuando existen operaciones simultaneas sobre los mismos registros.
- Se debe mantener un orden consistente al adquirir bloqueos para reducir el riesgo de interbloqueos.
- Es necesario gestionar los errores y revertir las transacciones cuando corresponda.
- La implementacion debe probarse con solicitudes concurrentes para verificar su comportamiento.

## 9. Resultado

Se establece el uso de transacciones y bloqueos de registros en el backend para proteger las operaciones que modifican el inventario.

Las operaciones de prestamo y devolucion deberan cumplir los procedimientos definidos en este registro para mantener la integridad de la informacion.

Este registro documenta una decision arquitectonica y no constituye evidencia de que los mecanismos de concurrencia esten implementados o hayan superado pruebas.
