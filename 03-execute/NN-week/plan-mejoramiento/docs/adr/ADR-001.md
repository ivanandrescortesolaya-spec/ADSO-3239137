## 2. Context

The Music School project requires the development of a system to manage the lending and return of musical instruments.

The solution must support the management of categories, instruments, students, loans, returns, inventory, and reports.

To organize development, an architecture must be established that separates the responsibilities of the user interface, business logic, data persistence, and infrastructure.

It is also necessary to facilitate communication between components, maintain data integrity, and enable integrated execution of the project.

## 3. Problem

An architecture and a set of technologies must be selected to develop the system in an organized, maintainable manner consistent with the defined requirements.

The decision must establish how the components will communicate and what responsibilities each component will have, preventing the user interface from directly accessing the database or implementing business rules that belong to the backend.

## 4. Decision

A client-server architecture with a layered separation of responsibilities is adopted, using the following technological components:

| Component | Technology | Responsibility |
|---|---|---|
| Frontend | React | User interface and information presentation. |
| Backend | PHP and Laravel | REST API, validations, and business rules. |
| Database | MySQL | Persistent storage of information. |
| Communication | HTTP and JSON | Information exchange between frontend and backend. |
| Infrastructure | Docker Compose | Configuration and integrated execution of services. |
| Public Website | Static Application | General presentation of the project. |

The backend will organize its responsibilities into layers to separate request handling, business logic, and data access.

The frontend will consume the endpoints defined in `api-contract.md` and will not have direct access to MySQL.

Business rules will be centralized in the backend to maintain consistent behavior regardless of the interface used.

From the project root, Docker Compose will coordinate the services required to run the system using a single command. Before running it, prepare the required environment files as described in `README.md` (including `infra/.env` and the API environment file):

```bash
docker compose --env-file infra/.env -f infra/docker-compose.yml up -d
```

## 5. Alternatives Considered

| Alternative | Reason for Not Selecting It |
|---|---|
| Use a single project for frontend and backend | Reduces the separation of responsibilities and makes it more difficult to maintain independent components. |
| Implement the backend with Node.js and Express | Does not align with the PHP and Laravel technologies established for this project. |
| Use a microservices architecture | Would introduce additional communication and deployment complexity that is not considered necessary for the defined scope. |
| Use PostgreSQL instead of MySQL | MySQL is maintained as the persistence technology established in the project's architecture. |

## 6. Justification

The decision allows the system's responsibilities to be separated while maintaining centralized communication through a REST API.

React will be used to build the user interface, while Laravel will be responsible for processing requests, applying validations, and enforcing business rules.

MySQL will store the information associated with the entities defined in `data-model.md`.

Communication through HTTP and JSON will facilitate integration between the frontend and backend.

Docker Compose will organize the services and simplify the preparation of the execution environment.

This architecture remains consistent with the requirements, data model, and API contract established for Music School.

## 7. Consequences

### Positive Consequences

- Separation of responsibilities between frontend, backend, and persistence.
- Centralization of business rules in the backend.
- Communication defined through a REST API.
- Organization of components to facilitate maintenance.
- Integrated execution through Docker Compose.
- Ability to verify each component independently.

### Consequences and Considerations

- The API contract must be kept up to date whenever available operations change.
- The frontend depends on API availability to retrieve and modify information.
- Services require connection configurations and environment variables.
- Integration through Docker Compose requires verification of dependencies and communication between containers.
