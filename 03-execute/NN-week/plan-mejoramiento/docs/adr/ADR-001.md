## 2. Contexto

El proyecto Music School requiere desarrollar un sistema para gestionar el prestamo y la devolucion de instrumentos musicales.

La solucion debe permitir administrar categorias, instrumentos, estudiantes, prestamos, devoluciones, inventario y reportes.

Para organizar el desarrollo se necesita establecer una arquitectura que permita separar las responsabilidades de la interfaz de usuario, la logica de negocio, la persistencia de datos y la infraestructura.

Tambien se requiere facilitar la comunicacion entre los componentes, mantener la integridad de la informacion y permitir la ejecucion integrada del proyecto.

## 3. Problema

Se necesita seleccionar una arquitectura y un conjunto de tecnologias que permitan desarrollar el sistema de manera organizada, mantenible y coherente con los requisitos definidos.

La decision debe establecer como se comunicaran los componentes y que responsabilidades tendra cada uno, evitando que la interfaz de usuario acceda directamente a la base de datos o implemente reglas de negocio que corresponden al backend.

## 4. Decision

Se adopta una arquitectura cliente-servidor con separacion de responsabilidades por capas y los siguientes componentes tecnologicos:

| Componente | Tecnologia | Responsabilidad |
|---|---|---|
| Frontend | React | Interfaz de usuario y presentacion de informacion. |
| Backend | PHP y Laravel | API REST, validaciones y reglas de negocio. |
| Base de datos | MySQL | Almacenamiento persistente de la informacion. |
| Comunicacion | HTTP y JSON | Intercambio de informacion entre frontend y backend. |
| Infraestructura | Docker Compose | Configuracion y ejecucion integrada de los servicios. |
| Sitio publico | Aplicacion estatica | Presentacion general del proyecto. |

El backend organizara sus responsabilidades mediante capas para separar la recepcion de solicitudes, la logica de negocio y el acceso a los datos.

El frontend consumira los endpoints definidos en `api-contract.md` y no tendra acceso directo a MySQL.

Las reglas de negocio se centralizaran en el backend para mantener un comportamiento consistente independientemente de la interfaz utilizada.

Docker Compose permitira coordinar los servicios necesarios para ejecutar el sistema mediante un unico comando:

`docker compose up -d`

## 5. Alternativas consideradas

| Alternativa | Motivo para no seleccionarla |
|---|---|
| Utilizar un unico proyecto para frontend y backend | Reduce la separacion de responsabilidades y dificulta mantener componentes independientes. |
| Implementar el backend con Node.js y Express | No corresponde con la tecnologia PHP y Laravel establecida para este proyecto. |
| Utilizar una arquitectura de microservicios | Introduciria una complejidad adicional de comunicacion y despliegue que no se considera necesaria para el alcance definido. |
| Utilizar PostgreSQL en lugar de MySQL | Se mantiene MySQL como tecnologia de persistencia establecida en la arquitectura del proyecto. |

## 6. Justificacion

La decision permite separar las responsabilidades del sistema y mantener una comunicacion centralizada mediante una API REST.

React se utilizara para construir la interfaz de usuario, mientras que Laravel sera responsable de procesar las solicitudes, aplicar las validaciones y ejecutar las reglas de negocio.

MySQL permitira almacenar la informacion de las entidades definidas en `data-model.md`.

La comunicacion mediante HTTP y JSON facilitara la integracion entre frontend y backend.

Docker Compose permitira organizar los servicios y simplificar la preparacion del entorno de ejecucion.

Esta arquitectura mantiene correspondencia con los requisitos, el modelo de datos y el contrato de API establecidos para Music School.

## 7. Consecuencias

### Consecuencias positivas

- Separacion de responsabilidades entre frontend, backend y persistencia.
- Centralizacion de las reglas de negocio en el backend.
- Comunicacion definida mediante una API REST.
- Organizacion de los componentes para facilitar su mantenimiento.
- Ejecucion integrada mediante Docker Compose.
- Posibilidad de verificar cada componente de forma independiente.

### Consecuencias y consideraciones

- Se requiere mantener actualizado el contrato de API cuando cambien las operaciones disponibles.
- El frontend depende de la disponibilidad de la API para consultar y modificar informacion.
- Los servicios necesitan configuraciones de conexion y variables de entorno.
- La integracion mediante Docker Compose requiere verificar las dependencias y la comunicacion entre contenedores.
