## 2. Contexto

El proyecto Music School requiere desarrollar un sistema para gestionar el préstamo y la devolución de instrumentos musicales.

La solución debe permitir administrar categorías, instrumentos, estudiantes, préstamos, devoluciones, inventario y reportes.

Para organizar el desarrollo se necesita establecer una arquitectura que permita separar las responsabilidades de la interfaz de usuario, la lógica de negocio, la persistencia de datos y la infraestructura.

También se requiere facilitar la comunicación entre los componentes, mantener la integridad de la información y permitir la ejecución integrada del proyecto.

## 3. Problema

Se necesita seleccionar una arquitectura y un conjunto de tecnologías que permitan desarrollar el sistema de manera organizada, mantenible y coherente con los requisitos definidos.

La decisión debe establecer cómo se comunicarán los componentes y qué responsabilidades tendrá cada uno, evitando que la interfaz de usuario acceda directamente a la base de datos o implemente reglas de negocio que corresponden al backend.

## 4. Decisión

Se adopta una arquitectura cliente-servidor con separación de responsabilidades por capas y los siguientes componentes tecnológicos:

| Componente | Tecnología | Responsabilidad |
|---|---|---|
| Frontend | React | Interfaz de usuario y presentación de información. |
| Backend | PHP y Laravel | API REST, validaciones y reglas de negocio. |
| Base de datos | MySQL | Almacenamiento persistente de la información. |
| Comunicación | HTTP y JSON | Intercambio de información entre frontend y backend. |
| Infraestructura | Docker Compose | Configuración y ejecución integrada de los servicios. |
| Sitio público | Aplicación estática | Presentación general del proyecto. |

El backend organizará sus responsabilidades mediante capas para separar la recepción de solicitudes, la lógica de negocio y el acceso a los datos.

El frontend consumirá los endpoints definidos en `api-contract.md` y no tendrá acceso directo a MySQL.

Las reglas de negocio se centralizarán en el backend para mantener un comportamiento consistente independientemente de la interfaz utilizada.

Docker Compose permitirá coordinar los servicios necesarios para ejecutar el sistema mediante un único comando:

`docker compose up -d`

## 5. Alternativas consideradas

| Alternativa | Motivo para no seleccionarla |
|---|---|
| Utilizar un único proyecto para frontend y backend | Reduce la separación de responsabilidades y dificulta mantener componentes independientes. |
| Implementar el backend con Node.js y Express | No corresponde con la tecnología PHP y Laravel establecida para este proyecto. |
| Utilizar una arquitectura de microservicios | Introduciría una complejidad adicional de comunicación y despliegue que no se considera necesaria para el alcance definido. |
| Utilizar PostgreSQL en lugar de MySQL | Se mantiene MySQL como tecnología de persistencia establecida en la arquitectura del proyecto. |

## 6. Justificación

La decisión permite separar las responsabilidades del sistema y mantener una comunicación centralizada mediante una API REST.

React se utilizará para construir la interfaz de usuario, mientras que Laravel será responsable de procesar las solicitudes, aplicar las validaciones y ejecutar las reglas de negocio.

MySQL permitirá almacenar la información de las entidades definidas en `data-model.md`.

La comunicación mediante HTTP y JSON facilitará la integración entre frontend y backend.

Docker Compose permitirá organizar los servicios y simplificar la preparación del entorno de ejecución.

Esta arquitectura mantiene correspondencia con los requisitos, el modelo de datos y el contrato de API establecidos para Music School.

## 7. Consecuencias

### Consecuencias positivas

- Separación de responsabilidades entre frontend, backend y persistencia.
- Centralización de las reglas de negocio en el backend.
- Comunicación definida mediante una API REST.
- Organización de los componentes para facilitar su mantenimiento.
- Ejecución integrada mediante Docker Compose.
- Posibilidad de verificar cada componente de forma independiente.

### Consecuencias y consideraciones

- Se requiere mantener actualizado el contrato de API cuando cambien las operaciones disponibles.
- El frontend depende de la disponibilidad de la API para consultar y modificar información.
- Los servicios necesitan configuraciones de conexión y variables de entorno.
- La integración mediante Docker Compose requiere verificar las dependencias y la comunicación entre contenedores.
