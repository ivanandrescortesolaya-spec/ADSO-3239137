
# ADR-003 — Historical Record Preservation and Logical Deactivation

## 1. Record Information

- **Code:** ADR-003
- **Title:** Historical Record Preservation and Logical Deactivation
- **Date:** 09/11/2026
- **Version:** 1.0
- **Status:** Accepted
- **Project:** Music School

## 2. Context

Music School must preserve information about instrument loans and returns to support queries, reports, and tracking of completed operations.

During system operation, catalog data may change, such as modifications to an instrument's name or information. It may also be necessary to remove an instrument from the catalog without losing the records of operations in which it was involved.

For this reason, a strategy is needed to protect historical records and prevent the accidental deletion of information related to loans and returns.

## 3. Problem

If loan or return records are physically deleted, the system may lose information required to retrieve previous operations and generate reports.

Similarly, deleting an instrument that has associated loans may affect relationships between tables and compromise data integrity.

It is also necessary to prevent subsequent catalog changes from modifying the historical information of an operation that has already been completed.

## 4. Decision

Music School will preserve historical records through the following measures:

1. **Loans:** Records in the `loans` table will not be physically deleted.
2. **Returns:** Records in the `returns` table will not be physically deleted.
3. **Instruments:** When an instrument must be removed from the catalog, logical deactivation will be performed using the `is_active = false` field.
4. **Historical Records:** Reference data stored in loan records will be preserved as a snapshot of the information that existed at the time of the operation.
5. **Relationships:** Foreign keys will use `ON DELETE RESTRICT` constraints to prevent physical deletions that could affect related records.
6. **Loan Status:** Loan status will be determined by the existence of an associated record in `returns`. A loan will be considered overdue when its due date has passed and no return has been registered.

Logical deactivation of instruments will not delete their associated loans or returns.

## 5. Alternatives Considered

### Alternative A: Physical Deletion of Records

Permanently delete instruments, loans, or returns when they are no longer used.

**Disadvantage:** This may cause the loss of historical information and affect referential integrity.

### Alternative B: Logical Deactivation for All Records

Add an activity indicator to all entities and preserve records through deactivation.

**Disadvantage:** This increases query complexity, and applying the same mechanism to historical loan and return records is unnecessary.

### Alternative C: Logical Deactivation of Catalog Items and Historical Record Preservation

Deactivate instruments using `is_active = false` while physically preserving loan and return records.

**Advantage:** This protects historical records, maintains relationships between records, and allows instruments to be removed from the catalog without losing information.

**Decision:** Alternative C is selected.

## 6. Justification

This decision helps maintain data integrity and preserve the traceability of operations performed in Music School.

Logical deactivation allows instruments to be removed from the catalog without affecting previous loans. Preserving loan and return records facilitates historical queries and report generation.

Additionally, the reference data stored in each loan makes it possible to retrieve the information associated with the operation at the time it was registered, even if catalog data is subsequently updated.

## 7. Consequences

### Positive Consequences

- Historical loan and return records are preserved.
- Information loss caused by accidental physical deletion is prevented.
- Relationship integrity is maintained through foreign keys.
- Instruments removed from the catalog can retain their previous operations.
- Historical report generation is facilitated.
- Subsequent catalog changes do not alter the data snapshots stored in previous operations.

### Considerations

- Catalog queries must exclude inactive instruments when appropriate.
- Inactive instruments cannot be used for new loans.
- Historical records must remain available for authorized queries.
- The application must enforce deletion restrictions in both backend logic and the database.

## 9. Outcome

It is established as a design decision that Music School will use logical deactivation to remove instruments from the catalog and will physically preserve loan and return records.

This decision must be followed during the implementation of the backend, data model, migrations, and system tests.

**Note:** This ADR documents a design decision. By itself, it does not demonstrate that the strategy has already been implemented or that it has passed automated tests.
